# Decisiones arquitectónicas

Las decisiones arquitectónicas indican cómo se organizará el sistema para responder a los drivers identificados.

Cada decisión tiene un identificador ADR, que significa Registro de Decisión Arquitectónica. Se explica qué se elige, por qué y qué resultado se espera, considerando también sus principales compromisos. Las decisiones con mayor impacto incluyen, en el apartado 2, las alternativas evaluadas y el motivo por el que se descartaron.

## 1. Registro de decisiones

| ADR-001 | **Organizar el backend como un monolito modular.** | DA01 – Crecimiento; DA04 – Integridad de contrataciones; DA08 – Cambios y ampliaciones. | Permite comenzar con una aplicación de servidor y separar las funciones por módulos. Las operaciones que afectan a varios módulos, como aceptar una cotización, se confirman en una transacción local. Simplifica el despliegue, aunque los módulos se publican juntos. Su capacidad de crecimiento dependerá también de los recursos y del diseño de datos. | Backend dividido en diez módulos: Usuarios y acceso, Prestadores, Catálogo y búsqueda, Solicitudes y visitas, Cotizaciones, Contrataciones y acuerdos, Seguimiento y pagos registrados, Calificaciones, Notificaciones y Administración e incidencias. |
| ADR-002 | **Aplicar Clean Architecture en los módulos de negocio.** | DA06 – Sustitución de IA; DA08 – Cambios y ampliaciones. | Separa las reglas del negocio de frameworks, almacenamiento y proveedores externos. Requiere definir contratos y responsabilidades, por lo que se aplicará sin crear capas o interfaces innecesarias. | Organización en Dominio, Aplicación, Infraestructura y Presentación, con dependencias dirigidas hacia las reglas del negocio. |
| ADR-003 | **Separar la aplicación web del backend y comunicarlos mediante una API REST.** | DA07 – API REST; DA10 – Uso desde distintos dispositivos. | La interfaz presenta la información y el servidor controla permisos, validaciones y operaciones. Esta separación requiere mantener definidos los datos y errores que intercambian ambas partes. | Aplicación web conectada a una API REST. Las validaciones principales se realizan en el servidor y no dependen únicamente de la pantalla. |
| ADR-004 | **Utilizar una interfaz responsive y adaptar los pasos al tamaño del trabajo.** | DA09 – Servicios rápidos y obras grandes; DA10 – Uso desde distintos dispositivos. | Permite utilizar el mismo sistema desde diferentes pantallas. Se comparte el proceso de contratación, habilitando documentos y etapas cuando sean necesarios. | Atención breve para reparaciones pequeñas y opciones de mayor detalle para trabajos grandes, sin mantener dos sistemas independientes. |
| ADR-005 | **Usar una base de datos relacional y proteger las operaciones críticas con transacciones y restricciones.** | DA04 – Integridad de contrataciones; DA11 – Conservación de información. | Las solicitudes, cotizaciones y contrataciones necesitan relaciones consistentes. También se deben controlar acciones simultáneas y solicitudes repetidas, lo que exige diseñar y probar estas operaciones. | Guardado completo de la contratación, una sola contratación activa por solicitud y controles para que un reintento no duplique registros. | ADR-006 | **Centralizar la autenticación y comprobar permisos en cada operación protegida.** | DA03 – Protección de cuentas, documentos y operaciones. | Además del perfil, se debe comprobar si el usuario participa en la operación. Este control debe mantenerse en todos los puntos de acceso, aunque la interfaz oculte botones. | Acceso según identidad, permisos y participación. | ADR-007 | **Integrar IA, notificaciones y mapas mediante contratos y adaptadores.** | DA05 – Fallas externas; DA06 – Sustitución de IA; DA08 – Cambios y ampliaciones. | Permite limitar la dependencia de cada proveedor y controlar errores y tiempos de espera. Cada integración necesita su propia traducción de datos y sus pruebas. | Servicios externos reemplazables, manejo de fallas y continuidad de las funciones independientes. Cada llamada tiene un tiempo límite y una alternativa de respaldo; ante fallas repetidas se suspenden temporalmente las llamadas al proveedor. Los reintentos se limitan a operaciones que puedan repetirse de forma segura. |
| ADR-008 | **Separar la interpretación de necesidades mediante IA de la consulta de prestadores.** | DA03 – Protección de información; DA06 – Sustitución de IA. | La IA orienta la búsqueda, pero puede producir interpretaciones incorrectas. | ADR-009 | **Registrar las notificaciones pendientes y enviarlas después de confirmar la operación principal.** | DA05 – Continuidad ante fallas externas; DA11 – Historial. | Evita que un error de envío haga aparecer como fallida una contratación ya guardada. Envíos con reintentos controlados y registro del resultado. |
| ADR-010 | **Utilizar índices, filtros y paginación en las consultas.** | DA01 – Crecimiento; DA02 – Consultas rápidas. | Reduce la información procesada y enviada en cada búsqueda. | ADR-011 | **Guardar los archivos fuera de las tablas y controlar su acceso desde el backend.** | DA03 – Protección de documentos; DA11 – Documentos y evidencias. | Las fotografías y documentos se gestionan como archivos, mientras la base de datos conserva sus referencias. Esta separación requiere coordinar permisos, respaldos y eliminación de archivos sin uso. | Archivos con validación de tipo, tamaño y acceso. Puede utilizarse almacenamiento local controlado o un proveedor externo, según las necesidades del despliegue. |
| ADR-012 | **Conservar versiones de los acuerdos y separar el historial del trabajo de la auditoría administrativa.** | DA04 – Cambios aceptados; DA11 – Historial y auditoría. | Las partes necesitan consultar las condiciones aceptadas y la administración debe revisar sus propias acciones. | ADR-013 | **Utilizar NestJS, React y PostgreSQL como stack tecnológico.** | DA04 – Integridad de contrataciones; DA07 – API REST; DA08 – Cambios y ampliaciones. | NestJS (TypeScript) organiza el backend en módulos e inyecta dependencias, lo que facilita el monolito modular y Clean Architecture. Un mismo lenguaje en frontend y backend reduce el costo de aprendizaje, a cambio de depender del ecosistema de Node.js. | Backend NestJS desplegado en contenedores Docker, aplicación web React + Vite, base de datos PostgreSQL, caché Redis, pruebas con Vitest o Jest, Playwright y k6, e integración continua con GitHub Actions. Los proveedores de IA, notificaciones y mapas se eligen al implementar cada integración. |

## 2. Alternativas consideradas

| Decisión | Alternativa | Motivo por el que se descartó |
|---|---|---|
| ADR-001 · Monolito modular | Monolito tradicional sin módulos | Mezcla responsabilidades: un cambio puede afectar a todo el sistema y dificulta DA08. |
| ADR-001 · Monolito modular | Microservicios | Aceptar una cotización tendría que coordinar varios servicios con transacciones distribuidas o sagas, lo que complica DA04. Exige más infraestructura, monitoreo y despliegues de los que justifica el proyecto. Queda como evolución posible: un módulo con límites claros puede extraerse después. |
| ADR-002 · Clean Architecture | Arquitectura en capas tradicional | Las reglas del negocio dependerían directamente de la base de datos y de los proveedores, lo que dificulta DA06 y las pruebas. |
| ADR-002 · Clean Architecture | Reglas en los controladores del framework (MVC) | La lógica de contratación quedaría repartida entre controladores y pantallas, y un cambio de framework afectaría las reglas. |
| ADR-005 · Base de datos relacional | Base de datos NoSQL de documentos | Las solicitudes, cotizaciones y contrataciones tienen relaciones fuertes, y DA04 necesita transacciones y restricciones de unicidad entre ellas. |
| ADR-009 · Avisos pendientes en la base de datos | Enviar el aviso dentro de la misma operación | Una falla del proveedor haría fallar o deshacer una contratación correcta. |
| ADR-013 · Stack tecnológico | Spring Boot (Java) | Es robusto y maduro, pero exige un segundo lenguaje distinto del frontend y más configuración para un equipo pequeño. |
| ADR-013 · Stack tecnológico | Django (Python) | Agiliza el desarrollo, pero su organización por aplicaciones y su ORM acoplan más las reglas al framework, lo que dificulta aplicar Clean Architecture. |
| ADR-009 · Avisos pendientes en la base de datos | Servicio de colas independiente (por ejemplo, RabbitMQ) | Agrega otro componente que operar sin una necesidad medida. Se reconsiderará si el volumen de avisos lo justifica. |

ADR-003 responde a la restricción RC06, que exige comunicar la aplicación web y el backend mediante una API REST; por eso no se evaluaron otros mecanismos de comunicación.
